Visualizing (and Checking) the Coverage Map

Three viable ways to see whether every record is covered — plus a no-visual, markdown-native check that scales better than any of them.

What the highlighted block actually is. It is not a chart request — it is a set of cardinality constraints over a multipartite graph. Each entity type (competency, use case, example, assessment, activity, prep reading, day, template) is a set of nodes; each "has at least one …" / "has exactly one …" line is a required edge with a count rule. "Coverage" = no node violates its rule. That framing is what makes all four approaches below possible, and it is why the honest answer to "can I check this without visuals?" is yes, and you probably should.

The model in one picture

Before choosing a visualization, name the graph. Nodes are typed; edges carry a minimum (and sometimes a maximum) count. Everything downstream is just a view over this.

Three viable visualization methods

Method 1

Coverage matrix (heatmap)

One relationship pair at a time.

  • Exhaustive & auditable
  • Empty row/column = the gap, instantly
  • One grid per relation (9+ grids)
Method 2

Multipartite node-link graph

The whole web at once.

  • Orphans literally float free
  • Shows the structure, not just gaps
  • Hairball past ~100 nodes
Method 3

Coverage dashboard (rule meters)

"Am I done yet?" at a glance.

  • Scales to any size
  • Names the exact offenders
  • Hides structure / relationships

Method 1 — Coverage matrix / heatmap

Put one entity type on the rows, the type it must link to on the columns, and fill a cell when the edge exists. A row sum of 0 is a coverage gap for a "≥1" rule; a row sum ≠ 1 is a gap for an "exactly one" rule. Column sums catch the reverse (e.g. an activity template with no instance). This is the workhorse for auditing a single constraint thoroughly.

Method 2 — Multipartite node-link graph

Lay each entity type in its own column and draw the edges. Anything a rule requires shows up as a line; anything missing a required line is an orphan and is trivial to spot once you color violators. Unlike the matrix, this shows several relations at once and reveals structure ("this one activity is carrying six competencies"), at the cost of getting busy at full scale.

Method 3 — Coverage dashboard (rule meters + offender lists)

Give each rule from your spec its own meter: satisfied nodes over total, plus the names of the ones that fail. This is the view that answers "how close is the whole course to done?" and it is the only one of the three that stays readable at 70 competencies × 9 rules. It hides structure entirely — you can't see which activity covers which competency — so it pairs naturally with Method 1 or 2 for drill-down.

Honorable mention: Sankey / alluvial

If you care about flow — how 70 competencies fan into 30 activities and land on 36 days — a Sankey shows band widths and where flow thins to nothing. It's prettier than useful for gap-finding (a zero-width band is easy to miss), so treat it as a communication artifact for stakeholders, not your working audit. Mermaid supports it (sankey-beta) straight from markdown.

Update — two of the new rules aren't cardinality. They're ordering.

The revised spec added two rules that none of the three views above natively handle, because they're not about counts — they're about position in time:

  • Teach-before-assess — "for every competency an assessment measures, some activity teaching it exists on an earlier day." A count can be satisfied while the order is still wrong.
  • Prerequisites — a sparse, mostly-on-assessments DAG. Ordering again, and it can contain cycles, which a cardinality check can't even see.

The cheap fix costs no new view: give the day axis meaning. Order the "Day" column of the node-link graph (M2) by real day index, and a violation becomes an edge that points backward in time — as visible as an orphan was. A dedicated timeline lane makes it unmissable:

Yes — you can check coverage with no visuals at all

This is the recommendation, not an afterthought. A coverage rule is a testable assertion, so treat the whole map like a test suite: parse the markdown, build the graph, assert every rule — cardinality, ranges, and the two ordering rules alike — and print the violations. A visualization is for exploring; a linter is for guaranteeing. You want both, but the linter is the one that keeps the map honest as it grows — and it is the only practical way to enforce teach-before-assess and prereq order across 36 days.

Step 1 — make the markdown machine-readable

Keep records exactly where they are, but give each one a tiny YAML frontmatter block with typed links (the same [[wikilink]] convention your notes already use). Nothing here stops it being a normal, human-editable markdown file.

---
id: C3
type: competency
title: Evaluation & tracing
assessments: []              # <- empty: this is the gap
activities: [act-eval-harness]
---
Students can instrument an agent run and read a trace...
---
id: D18
type: day
day: 18                           # <- the ordering key: teach-before-assess
                                  #    and prereqs are checked against this
prep_reading: [r-langgraph-intro] # 0 or 1
practice: [act-eval-harness]      # >=1
in_class: [demo-tracing, pair-debug]   # 1 or 2
examples: [ex-trace-reader]       # >=1
---

Give every schedulable node (day, activity, assessment) a day: integer — it's the single field that makes both new ordering rules checkable. Prereq edges live on the node that depends on them: prereqs: [A1].

Step 2 — assert the rules

~40 lines of Python (or a Quarto/pandas pass, since you already use .qmd) turns the whole spec into pass/fail. The rules map one-to-one onto the highlighted block.

import glob, yaml, sys
from collections import defaultdict

nodes = {}
for path in glob.glob("course_design/**/*.md", recursive=True):
    fm = read_frontmatter(path)          # split on '---'
    if fm and "id" in fm:
        nodes[fm["id"]] = fm

day_of = {n["id"]: n.get("day") for n in nodes.values()}   # day index per node

def count(node, field, lo=1, hi=None):                     # range check (hi=None = unbounded)
    n = len(node.get(field, []) or [])
    return (n >= lo and (hi is None or n <= hi)), n

hard, soft = [], []
for node in nodes.values():
    t, nid = node["type"], node["id"]
    if t == "competency":
        for f in ("assessments", "activities"):
            ok, n = count(node, f)
            if not ok: hard.append((nid, f"needs >=1 {f}, has {n}"))
    if t == "use_case":
        for f in ("examples", "days", "case_studies"):
            ok, n = count(node, f)
            if not ok: hard.append((nid, f"needs >=1 {f}, has {n}"))
    if t == "prep_reading":
        ok, n = count(node, "days", 1, 1)      # exactly one
        if not ok: hard.append((nid, f"needs exactly 1 day, has {n}"))
        ok, n = count(node, "competencies")     # NEW: >=1 competency
        if not ok: hard.append((nid, f"needs >=1 competency, has {n}"))
    if t == "day":                              # NEW ranges — soft ('most days')
        for f, lo, hi in [("prep_reading",0,1), ("practice",1,None),
                          ("in_class",1,2), ("examples",1,None)]:
            ok, n = count(node, f, lo, hi)
            if not ok: soft.append((nid, f"day {f}: want {lo}..{hi or '∞'}, has {n}"))

# NEW rule 1 — teach-before-assess (ordering, not a count)
for a in [n for n in nodes.values() if n["type"] == "assessment"]:
    d_assess = day_of[a["id"]]
    for comp in a.get("competencies", []):
        taught = [act for act in nodes.values()
                  if act["type"] == "activity" and comp in act.get("competencies", [])
                  and day_of.get(act["id"], 1e9) < d_assess]
        if not taught:
            hard.append((a["id"], f"measures {comp} but nothing teaches it before day {d_assess}"))

# NEW rule 2 — prereqs must land on earlier days + no cycles (topo sort)
edges = {n["id"]: n.get("prereqs", []) for n in nodes.values()}
for nid, pres in edges.items():
    for p in pres:
        if day_of.get(p, -1) >= day_of.get(nid, 1e9):
            hard.append((nid, f"prereq {p} is not on an earlier day"))
if has_cycle(edges):                            # Kahn / DFS — a cardinality check can't see this
    hard.append(("GRAPH", "prerequisite cycle detected"))

for vid, msg in hard: print(f"  {vid}: {msg}")
for vid, msg in soft: print(f"  ~ {vid}: {msg}  (soft)")
sys.exit(1 if hard else 0)                       # soft warnings don't fail the build

Step 3 — read the report

The output is the coverage status — the same offenders the dashboard chips showed, in plain text a script (or a person) can act on. Exit-code it and drop it in a pre-commit hook or CI so a gap can never silently ship.

The last two hard lines are the payoff of the update: they're the failures no matrix or dashboard could surface, because they're about when a node sits, not how many edges it has.

Zero-code option. If you keep the records in an Obsidian vault, a Dataview query does the same thing without a script — e.g. TABLE assessments WHERE type="competency" AND length(assessments)=0 renders a live gap table that updates as you edit. And a Mermaid graph block gives you Method 2 in the same file. Between Dataview (the linter/matrix) and Mermaid (the graph), a plain markdown vault covers three of these four approaches with no build step.

Recommendation

  1. Source of truth: markdown records with frontmatter + [[wikilinks]]. Never let a visualization become the master copy.
  2. Add a day: index to every schedulable node — it's cheap and it's the one field that turns the two new ordering rules (teach-before-assess, prereqs) from unenforceable into a topological sort. Without it, those rules can only be eyeballed.
  3. Guarantee: the Step-2 linter, wired to exit non-zero, run on every commit. This is what actually keeps the full rule set — cardinality, ranges, and ordering — honest. The ordering rules in particular have no human-scalable alternative.
  4. Explore & communicate: the dashboard (M3) as your day-to-day "how done am I" view (it reuses the linter's parsed graph), the matrix (M1) when you need to certify a single rule, and the day-ordered node-link (M2) — free via Obsidian/Mermaid — when you want to feel the structure and catch backward edges by eye.
  5. On templates: your open question — include templates in the map, but as a soft rule (template → ≥1 instance) that warns rather than fails. A template with no instance is a smell, not a broken course.
